## 1. 为什么要改

v1 用三条本地规则判断该不该关心（持续低谷 / 情绪回升 / 连续高光）。管道形状是对的，问题出在**规则在用数数的方式下情绪断言**。

| 问题 | 表现 |
|---|---|
| 情绪判断生硬 | 「连续三篇 sad = 持续低谷」本身就是粗暴的心理学断言 |
| 窗口缺失（真 bug） | `LowMoodStreakRule` 用 `fetchAll().prefix(3)`，**没有时间窗**。三个月里零散写的 3 篇 sad 也会被判成低谷 |
| 粒度错了 | 趋势是**天与天**之间的事。按篇计数时，一天写三篇就凑够了「连续三篇」，而那只是一天的情绪 |

解法**不是**删掉本地层把一切交给 AI（那会带来每次打开一次 API、无法测试、模型总想说话三个新问题），而是**把本地层的情绪判断权彻底拿掉**，让它退回去只管账。

---

## 2. 核心原则：决策权分层

> **AI 有一票否决权，没有一票通过权。**
> AI 可以说「这次不值得说」，但本地闸门不放行，它根本没有机会开口。

| 层 | 回答的问题 | 性质 |
|---|---|---|
| 本地闸门 | 有新蛋吗 / 天数够吗 / 刚说过吗 | 纯算术 · 可测 · 零 token |
| AI 决策 | 这段时间发生了什么 / 值不值得说 / 说什么 | 纯语义 · 结构化返回 |
| 本地边界 | 说过类似的吗 / 用户关了吗 / 安全级别 | 纯记账 · 产品红线 |

本地层不再声称自己懂情绪，「生硬感」消失；AI 拿到的是完整窗口而不是被规则预筛过的结论，语义理解能力才真正用得上。

## 3. 数据的三层

| 层 | 单位 | 何时产生 | 关怀怎么用 |
|---|---|---|---|
| 日记 `Post` | 一篇 | 写完即分析，返回 emotion + reply | **不直接使用** |
| 蛋 `DayEgg` | 一天 | 用户手动总结，或当天结束后 | **时间线的唯一单位** |
| 时间线 | 14 天 | 查询时派生 | 喂给 AI 的 payload |

> **铁律：关怀只看蛋，不看日记。**
> 单篇日记的 emotion 服务于写完那一刻的即时回应；蛋的总结情绪才是趋势的载体。

### 3.1 欠蛋判定（已实现）

判定规则收在一个纯函数里，`DayEggService` 和 `SquareViewModel` 共用同一份，避免两边漂移：

```swift
nonisolated enum EggDebt {
    static func owes(latestEntryAt: Date?, egg: DayEggRecord?) -> Bool {
        guard let latestEntryAt else { return false }   // 那天没写过 → 不欠
        guard let egg else { return true }              // 有日记没蛋 → 欠
        return egg.createdAt < latestEntryAt            // 蛋比日记旧 → 过时了，欠
    }
}
```

**用「蛋比最新日记旧」判定过期，不需要额外的 `summarizedAt` 标脏字段** —— 两个已有的时间戳一比就出来了。编辑历史日记若改动了 `createdAt`，同一条规则自动覆盖。

### 3.2 「当天结束后」实际发生在次日

App 不在后台运行，没有定时任务能在零点触发总结，所以真实落点是**次日打开 App 时补做**（`DayEggService.hatchAllPending`）。

> ### ⚠️ 顺序依赖 · 不能搞反
> 打开 App 时必须**先补完所有欠的总结，再跑关怀闸门**。顺序反了，AI 拿到的时间线就缺最新一天 —— **而最新一天恰恰是情绪反转最可能藏身的地方**。用户前几天低落、昨天好转，缺了昨天那颗蛋，弹出来的就是一句过时的「感觉你最近有点低落…」。
>
> 这条已经落在 `SceneDelegate.onAppActive()` 里，是实实在在的两行先后。

### 3.3 欠债规模：最多一天

写日记要调 AI，**没网就没有帖子**。所以债务的产生和偿还被同一个条件卡住：

```
周一  打开 App → 补蛋（无欠债）→ 写日记 → 周一欠一颗
周二  不打开
周三  打开 App → 补掉周一 ✅
```

稳态下**最多欠一天，就是最后写日记的那天**。`hatchAllPending` 的循环因此几乎总是跑 0 或 1 次，成本可以忽略。

它存在是为了**自愈异常累积的洞**：孵蛋失败、`DayEgg` 之前的历史数据、以及修好之前「只在广场页补蛋」留下的缺口。`.max()` 那种只补一颗的写法在结构上补不完，洞会永久留着。

## 4. 三段管道

```
① 本地闸门 ── 过闸 · 整个窗口原样带走，一天都不筛 ──▶
② AI 语义决策 ── shouldShow = true ──▶
③ 本地产品边界 ──▶ 立刻展示
```

### Layer 1 · 成本闸门（本地）

一条前置 + 三个条件全过，才发起 AI 调用。**整段代码里不允许出现任何 `emotion` 字样。**

```swift
func shouldAsk(now: Date) -> MoodWindow? {
    // 0. 前置：已有关怀挂着，别再生成第二条
    guard messages.active() == nil else { return nil }

    // 1. 自上次检查后有新蛋吗（是蛋，不是日记）
    guard eggs.count(after: lastCheckAt) > 0 else { return nil }

    // 2. 窗口内有蛋的天数够吗
    let window = eggs.fetch(since: now - 14.days)
    guard window.count >= 3 else { return nil }        // 3 天，不是 3 篇

    // 3. 距上一条关怀退休满 3 天了吗
    guard now.timeIntervalSince(lastRetiredAt) > 3.days else { return nil }

    return MoodWindow(eggs: window)                    // 一天都不筛
}
```

`lastCheckAt` 与 `lastRetiredAt` **不是独立存的状态**，是从日志表派生的（见第 6 节）。

### Layer 2 · 语义决策（AI）

拿到 14 天情绪时间线（**每天一行，最多 14 行**），做跨天的语义判断，返回结构化决策。可以选择「这次不说」。

### Layer 3 · 产品边界（本地）

文案去重、AI 总开关、安全级别处理。任何一条不过就丢弃并记录原因。

> **常见误解**：「本地粗筛」筛的**不是相关内容**，是**这次要不要花一次 API 调用**。窗口内的蛋全部交给 AI。需要按语义筛内容的是聊天检索（RAG），那是另一个系统。

## 5. 一条关怀的一生

> **铁律：关怀绝不出现在用户写日记的那次会话里。**
> 用户写完什么都不会发生；等他离开一阵子再回来，史莱姆才开口。史莱姆是在你不在的时候想起了你，不是盯着你写。

### 只有一个事件

| 事件 | 定义 | 做三件事 |
|---|---|---|
| `appOpened` | **进前台，且跨了自然天** | ① 补完欠的当天总结 ② 判断挂着的关怀是否该退休 ③ 闸门 → AI → 展示 |

`postSaved` 事件**将被删除**，写日记不再触发任何关怀逻辑。

> **`appOpened` 的定义不能含糊**
> 定成「切回前台」，用户写完日记切去微信、两分钟后回来关怀就弹出来，铁律当场作废。只算「冷启动」，iOS 用户几周不杀 App，关怀等不到机会。
> 取「**进前台 + 跨自然天**」，它对应的才是「你离开了一阵子又回来」这个真实时刻。
>
> 实现上入口统一放在 `sceneDidBecomeActive`（冷启动和后台返回都会触发），跨天判断交给闸门 —— **让入口简单，让各自的闸门去过滤**。

### 为什么在打开时才生成文案

v1 是写完日记就生成好文案存着，等下次打开再展示。致命场景：

```
日记 1–3: sad   → 生成「感觉你最近有点低落…」存着
日记 4:   happy → 用户心情已经好了
次日打开        → 弹出那句过时的低落关怀
```

把生成挪到展示的同一时刻，这个问题**连同一整批概念一起消失**：

| 原来的麻烦 | 现在 |
|---|---|
| 情绪反转导致文案过时 | 消失。AI 看到的永远是含最新一天的完整窗口 |
| 连写多篇烧多次 API | 消失。只在打开时调一次 |
| `pending` 排队 / 覆盖 / 更新 | 整个概念消失 |
| `postSaved` 事件 | 整个删掉 |

代价是卡片要等 AI 返回（1–3 秒）才滑出。**这其实是加分** —— 延迟两秒出现，读起来像史莱姆「想了一下才开口」。网络失败就这次不出现，用户不会知道自己错过了什么。

### 退场规则

只有两条，谁先到算谁：

| 条件 | 含义 |
|---|---|
| **下一颗蛋诞生** | 语境翻篇了。注意是**蛋**不是日记 —— 同一天再写一篇，蛋没换，关怀不该退场 |
| **生成后满 3 天** | 关怀内容有保质期。「感觉你最近那口气松了一点」三天后说就不新鲜了 |

> **为什么不需要「露面次数上限」**
> 3 天这个参数自己就是上限：用户一天开一次 App，最多看到同一句三次，第四天它自己走了。一个参数干两件事，因为保质期和露面上限本来就是同一件事的两面。也正因如此这个数不能放大 —— 设成 7 天就会出现「同一句关心看了七遍」。

### 两层寿命

| 层 | 规则 |
|---|---|
| **单次露面** | 进首页时滑出；用户一开始操作页面（滚动、点按钮、去写日记）就淡出，兜底 10 秒。**短，不挡路** |
| **整条寿命** | 跨会话存活，直到上面两条退场规则之一。**这次没看清，下次进首页它还在** |

退休之后也不蒸发 —— 按 AI 返回的 `referencedDates`，**沉淀回它所指的那几天的蛋上**，用户以后翻到那几天能看到「那阵子，我跟你说过这句话」。不必新开任何列表页。

### 状态只剩两个

`pending` 没了（不再有未展示的存货），`expired` 也没了（不存在「生成了却没机会展示」）。

```
跨天打开 App
   │
   ├─ ① 补完欠的当天总结
   ├─ ② 挂着的关怀该退休了吗
   └─ ③ 闸门 ──▶ AI ──▶ 展示 ──▶ shown（挂着，每次进首页都在）
                                   │
                   ┌───────────────┴───────────────┐
             下一颗蛋诞生                      生成满 3 天
                   │                               │
                   └──────────▶ retired ◀──────────┘
                                   │
                            沉淀到那几天的蛋上
```

## 6. AI 契约

### 输入

```json
{
  "近14天": [
    {"date":"08-06","emotion":"anxious","intensity":2,"summary":"方案改了三版，甲方还是不满意"},
    {"date":"08-09","emotion":"tired",  "intensity":3,"summary":"连着加班，周末也在改"},
    {"date":"08-12","emotion":"sad",    "intensity":2,"summary":"觉得自己是不是不适合这行"},
    {"date":"08-18","emotion":"calm",   "intensity":1,"summary":"改完了，去楼下吃了碗面"}
  ],
  "最近对ta说过的话": ["最近好像有点累呀，别硬撑着~"]
}
```

每行是一颗蛋的总结，**不发日记全文** —— 既是隐私设计（数据最小化），也把 payload 压到 1k token 以内。没有蛋的天直接缺席，缺口本身也是信息。

### 输出

```json
{
  "shouldShow": true,
  "pattern": "从持续压力中缓过来了",
  "confidence": 0.82,
  "message": "感觉你最近那口气好像终于松了一点点…",
  "referencedDates": ["08-12", "08-18"],
  "safety": "normal"
}
```

`confidence` **仅记录，禁止用作阈值**（见第 9 节）。`safety` 取值 `normal | concern | crisis`。

### Prompt 铁律

沿用 v1 的四条，全部保留：

1. **安全底线最高**。出现严重低落、绝望或自我伤害倾向时收起可爱腔，真诚回应并温柔建议寻求信任的人或专业帮助，同时 `safety` 升级。
2. **绝不暴露判断依据**。不出现「连续几天」「检测到」「记录显示」「数据」。
3. **探询不断言**。说「最近好像…」，不说「你一定…」。
4. **不说教、不给建议**，只表达陪伴。一句话，口语化。

新增第五条 —— **明确的「不说」清单**。这是压住模型「总想说点什么」倾向的关键，比任何置信度阈值都有效：

> 以下情况必须返回 `shouldShow: false`：情绪起伏在这个人的日常范围内；变化只有一两天、还看不出走向；你想说的话和「最近对 ta 说过的话」意思重复；你只能说出「要注意休息」这类放之四海皆准的空话。
> **宁可不说，也不要说一句正确但没用的话。**

### 失败降级

网络失败、JSON 解析失败、字段缺失 —— **一律视为「本次不展示」，不伪造、不重试轰炸**，但要写进 `CareCheck`。绝不能让 AI 故障变成一条奇怪的关怀弹在用户面前。

## 7. 数据模型改动

全部是 Core Data 轻量迁移，**不需要重建 store**。

### `DayEggStore` 补齐删除（切片 4）

```swift
func delete(for day: Date)
```

顺带修掉**孤儿蛋** bug：删光某天最后一篇日记后，那天的蛋还挂在周条上，且永远不会被清理（`EggDebt.owes(latestEntryAt: nil, ...)` 返回 `false`）。

### `CareMessage`

| 字段 | 类型 | 用途 |
|---|---|---|
| `status` | String | **两态**：`shown` / `retired` |
| `retiredAt` | Date? | 退休时刻。冷却期的锚点 |
| `referencedDates` | String | AI 引用的日期，逗号分隔。退休后靠它沉淀回那几天的蛋 |

### 新增实体 `CareCheck`

每次检查记一条，无论有没有真的调 AI。**没有它，你答不出「为什么昨天那条没弹」。**

| 字段 | 含义 |
|---|---|
| `checkedAt` | 什么时候检查的 |
| `gatePassed` / `gateReason` | 闸门有没有过、被哪一条挡下 |
| `aiCalled` / `aiRaw` | 有没有调 AI、原始返回 |
| `latencyMs` / `tokenCount` | 延迟与成本，可观测基础 |
| `finalShown` / `dropReason` | 最终展没展示、被哪条边界丢弃 |

### 删除实体 `RuleCooldown`

连同 `CooldownStore` 一起删。它要存的时间戳都是派生值：

| 需要的值 | 从哪来 |
|---|---|
| `lastCheckAt` | 最新一条 `CareCheck.checkedAt` |
| `lastRetiredAt` | 最新一条 `status == retired` 的 `CareMessage.retiredAt` |
| 当前挂着的关怀 | `status == shown` 的最新一条 |

**`expired` 不更新冷却锚点** —— 那条关怀用户压根没看到，不该占一个冷却期。

> **最终形态**：关怀相关的持久化只剩三张表 —— `DayEgg` / `CareMessage` / `CareCheck`。**没有任何独立的状态存储，日志即状态。**

## 9. 已知坑

**1 · `confidence` 不能当阈值**
模型自报的置信度校准极差，0.85 和 0.6 之间没有你以为的含义。`if confidence > 0.8` 的结果是它几乎永远大于 0.8。**只记录，不判断。**

**2 · 模型总想说点什么**
问它「要不要关心一下」，它的默认人格就是 helpful，`shouldShow: false` 出现频率会远低于预期。靠第 6 节那份「不说清单」压，不要靠阈值压。

**3 · 同一句话要经得起看三遍**
关怀最长挂 3 天，用户一天开一次就会看到三次同一句。这是「不会错过」的代价，但反过来是**一条文案约束**：第一遍戳心的话，第三遍可能显得刻意甚至做作。越含蓄、越留白的句子越经得起重看。**要写进 prompt，也要进 eval 抽查项。**

**4 · 打开 App 时最多两次 AI 调用**
先补蛋（最多 1 次，见 3.3）再跑关怀（最多 1 次）。**上限是 2 次，不是 N+1 次**，不需要额外限流。但补蛋必须先完成（3.2 的顺序依赖），且不该阻塞首页渲染 —— 首页照常显示，关怀卡片等两步都跑完再滑出。

## 10. 验收标准

| 项 | 方法 | 目标 |
|---|---|---|
| 闸门单测 | 注入 `now` 造蛋，断言前置与三个条件各自能挡下 | 全通过 |
| 顺序依赖 | 造「前几天低落 + 昨天好转但未总结」的场景，断言补完总结才跑闸门 | 不出现过时关怀 |
| 关怀决策 eval | 手工构造 20 个情绪时间线场景 + 标注「该不该关怀」，跑 precision / recall | precision 优先于 recall |
| 文案铁律 | 抽查：① 禁词「连续」「记录」「检测」② 是否经得起连看三遍 | 禁词 0 例 |
| 成本 | 从 `CareCheck` 统计：AI 调用次数 ÷ 跨天打开次数 | 闸门应拦下大部分 |

eval 的直接价值不是简历，是**你会立刻看到模型 recall 极高而 precision 很低** —— 有了这个数字，调 prompt 才有依据。
